## 第一部分：面试前分析策略

### 1.1 简历预分析（面试前完成）

拿到简历后，按以下5个维度做结构化预分析：

#### （1）职业轨迹扫描

画出候选人的完整时间线，标注每个阶段的**核心方向**：

```
时间 | 公司 | 岗位 | 核心方向 | 与JD相关度(高/中/低)
```

重点关注：
- **AI实际从业年限**：很多人写"10年研发经验"，但AI相关可能只有1-2年
- **转型节点**：什么时候开始做AI？是主动转型还是被动转岗？
- **公司背景验证**：大厂/创业公司/央企？不同背景的人技术深度差异很大

#### （2）项目真实性预判

对简历中每个核心项目，面试前准备3个层次的验证问题：

| 层次 | 问题类型 | 目的 |
|------|----------|------|
| **L1 做了什么** | 项目的业务背景、你负责什么、用了什么技术 | 验证参与度 |
| **L2 怎么做的** | 技术选型理由、架构设计思路、数据流是什么样的 | 验证技术深度 |
| **L3 为什么这么做** | 为什么不用方案B？遇到什么难点？怎么评估效果？ | 验证真实理解和决策能力 |

**红旗信号**（简历中可能注水的标志）：
- 只有项目列表，没有个人贡献描述
- 量化指标看似很高但缺乏baseline对比（如"准确率98%"——从多少提升到98%？）
- 用了热门技术栈但未说明具体使用场景
- 角色描述模糊（"参与"、"负责"、"主导"是三个完全不同的层级）

#### （3）量化指标解读

简历中出现的每一个量化指标，都要标注：
- ✅ **有baseline对比**（如"从80%提升至98%"）
- ⚠️ **有数字但无baseline**（如"准确率达98%"——原来多少？）
- ❌ **模糊指标**（如"显著提升"、"大幅优化"）

#### （4）技术栈覆盖度评估

对照JD核心技术能力要求，评估候选人技术栈的覆盖情况：

| JD核心能力 | 覆盖标记 |
|-----------|----------|
| 架构能力（分布式/微服务） | 🟢深度 / 🟡了解 / 🔴缺失 |
| 全栈技术理解（Redis/MQ/MySQL） | 🟢深度 / 🟡了解 / 🔴缺失 |
| AI工程化（智能体/LLM/RAG/函数调用） | 🟢深度 / 🟡了解 / 🔴缺失 |
| 模型训练/微调（SFT/DPO/蒸馏） | 🟢深度 / 🟡了解 / 🔴缺失 |
| 问题解决能力（性能优化/架构重构） | 🟢深度 / 🟡了解 / 🔴缺失 |

#### （5）联网验证

对关键信息做联网搜索验证：
- 论文：ACL Anthology / Google Scholar 搜索作者名
- 专利：Google Patents 搜索专利号
- 开源贡献：GitHub 搜索用户名
- 公司背景：天眼查/企查查
- 书籍/课程：豆瓣/极客时间验证
- 技术博客：个人网站/知乎/CSDN

## 第二部分：面试问题池

### 2.1 AI工程化核心能力

#### RAG（检索增强生成）

| # | 问题 | 考察点 | 期望回答要素 |
|---|------|--------|-------------|
| R1 | 你做RAG的完整数据流是什么样的？从用户提问到返回答案 | 闭环思维 | 查询→召回→重排→生成→后处理，每一步的技术选型 |
| R2 | 向量模型用的什么？为什么选这个？有没有做过模型评测对比？ | 模型选型能力 | 至少知道text-embedding-3-large、bge-m3、jina-embeddings等主流模型的优劣势 |
| R3 | 文档分块策略是什么？为什么？ | 分块策略理解 | 按字符/按段落/语义分块/递归分块，各自的优缺点 |
| R4 | 召回阶段是怎么做的？向量检索还是混合检索？ | 检索策略 | 向量相似度 + BM25关键词检索的混合策略，及各自的适用场景 |
| R5 | 阈值怎么取的？有没有量化标准？ | 评估方法论 | 不期望完美答案，但要有系统性思路，而非"纯靠调" |
| R6 | RAG的幻觉问题怎么解决？ | 工程化方案 | 提示词约束、溯源引用、后校验Agent、多轮检索、RAGAS评估 |
| R7 | embedding模型和re-ranker模型的区别？输入输出分别是什么？ | 核心概念 | embedding：文本→向量（检索用）；re-ranker：query+doc→相关性分数（精排用） |
| R8 | cosine相似度和点积的区别？应用上有什么区别？ | 基础数学 | cosine只看方向（归一化后），点积考虑模长；归一化向量上等价 |
| R9 | BM25和编辑距离了解吗？ | 检索基础 | BM25：基于词频的统计检索；编辑距离：字符串相似度 |
| R10 | 如果召回结果中有很多相似文档，怎么去重/过滤？ | 工程经验 | MMR（最大边际相关性）、聚类去重、相似度阈值 |

#### Agent / 智能体

| # | 问题 | 考察点 | 期望回答要素 |
|---|------|--------|-------------|
| A1 | ReAct是什么？你们项目中怎么用的？ | Agent基础 | Reasoning+Action循环，思考→行动→观察→再思考 |
| A2 | ReAct死循环怎么解决？ | 工程经验 | 步数限制+降级策略（非简单退出），可考虑切换到更简单的调用模式 |
| A3 | 什么场景必须用多Agent？什么场景单Agent就够了？ | 架构判断 | 多Agent：上下文隔离、专业分工、并行执行；单Agent：简单任务、低延迟场景 |
| A4 | 上下文管理有哪些策略？ | 工程经验 | 写文件+引用、对话裁剪、摘要压缩、滑动窗口、分级记忆 |
| A5 | 多Agent之间怎么通信？协调机制是什么？ | 系统设计 | 共享状态、消息传递、HTTP/gRPC、事件驱动 |
| A6 | Agent的准确率怎么评估？ | 评估方法论 | 黄金测试集+自动化评估+LLM-as-Judge+业务指标闭环 |
| A7 | 你用过哪些Agent框架？各有什么优劣势？ | 技术广度 | LangGraph、OpenClaw、SmolAgents、Claude Agent SDK等的适用场景 |

#### Prompt工程

| # | 问题 | 考察点 | 期望回答要素 |
|---|------|--------|-------------|
| P1 | 你写提示词有什么技巧？ | Prompt基本功 | 结构化（角色/任务/约束/示例）、CoT、Few-shot |
| P2 | 提示词大概多长？怎么迭代的？ | 实战经验 | 从短到长的迭代过程、A/B测试、回归测试 |
| P3 | 如果提示词明确要求了"基于知识库回答"但模型还是编造，怎么办？ | 工程化方案 | 提示词是第一层约束但不够：加溯源要求、后校验、降低温度、换用约束解码 |

#### 意图识别 / 路由

| # | 问题 | 考察点 | 期望回答要素 |
|---|------|--------|-------------|
| I1 | 意图识别是怎么做的？ | 系统性方案 | 正则（高频确定）→BERT分类（中等置信度）→大模型兜底（低置信度）三层架构 |

### 2.2 模型训练/微调

| # | 问题 | 考察点 | 期望回答要素 |
|---|------|--------|-------------|
| M1 | SFT和DPO的区别？ | 微调原理 | SFT：监督学习，学习输入→输出映射；DPO：偏好对齐，学习人类偏好排序 |

### 2.5 量化评估意识（贯穿全场）

**关键追问**（几乎适用于任何项目）：

```
Q1: 你做之前的效果是什么样的？（baseline）
Q2: 你做之后的效果是什么样的？（结果）
Q3: 这个提升是怎么测量出来的？（评估方法）
Q4: 有没有对照组？（科学性）
Q5: 如果现在让你重新做，有什么可以改进的？（反思）
```

### 2.6 排查题（场景诊断，C 类）

> 验证**诊断性深度**：生产故障场景下的假设树、排查顺序、信息澄清意识。与 A 类知识题（验"知不知道"）、B 类元能力题（验"不会时怎么反应"）互补——排障能力只能靠真排过坑，背书背不出来。分层时长与题型配比统一回指 `../SKILL.md` §分层标尺（SoT）及 Step 5；成题示例见 `定制面试题-示例.md` 第五部分。

**方法论速查：**

| 环节 | 要点 |
|------|------|
| **设计规则①** | 症状带误导性：表象指向 A、根因在 B（只背过 postmortem 的人会直奔 A） |
| **设计规则②** | 先要假设树、再要排查顺序：不让候选人直接给答案；每个假设必须配一个**最便宜的证伪手段** |
| **设计规则③** | 信息故意不足：留一个关键变量不给（版本/租户/日志片段/配置），看候选人问不问——**不问就开编 = 危险信号** |
| **判卷四行为** | ①先澄清 vs 开编 ②假设树 ≥3 分支且有序 ③判别成本从便宜到贵 ④知识边界坦白 |
| **题源纪律** | 优先用面试官自己修过的真 bug 脱敏出题（有 ground truth、外部背不到）；无积累时用下方通用题兜底 |
| **"没排过"处理** | 中性 ❓未覆盖，按层级处理；只有"不问澄清就开编"才是危险信号 |

**通用追问链**（拿到任何排查题答案后往下钻）：

```
1. 你说的第一步，具体看什么字段/日志？—— 验证真做过还是背的
2. 如果第一步结果正常，下一个分支是什么？—— 验证假设树的完备性
3. 你的排查顺序为什么这么排？—— 验证判别成本意识
4. 有没有你还没问、但你需要知道的信息？—— 主动给信息缺口机会，看意识
```

**通用领域成题**（任何 AI 工程团队可复用；用时按团队真实故障替换为脱敏真 bug）：

#### T1 新模型上线后准确率下降

| 栏目 | 内容 |
|------|------|
| **题面（口述）** | "模型服务从 v2 换到 v3 后，监控显示某类问题准确率从 88% 掉到 71%，但另一类问题反而变好了。怎么定位？" **（故意不说：prompt 模板、评测集构成、temperature）** |
| **考察点** | 变更归因思维 + "一类变好一类变坏 = 分布差异"的推理 |
| **好答案的形状** | 先问澄清：准确率怎么测的（评测集是谁的口径）？prompt 改过吗？两版 temperature 等采样参数一致吗？→ 分层：评测集是否只覆盖旧模型擅长的分布 / prompt 对 v3 的指令敏感度 / 采样参数差异；给出"先对齐变量再归因"的顺序 |
| **危险信号** | 直接断言"v3 不行"回滚了事；不问评测集口径；想不到采样参数这类隐藏变量 |

#### T2 检索质量缓慢劣化

| 栏目 | 内容 |
|------|------|
| **题面（口述）** | "知识库问答系统上线半年，检索质量缓慢下滑，用户抱怨逐渐变多，没有任何变更记录。思路？" **（故意不说：文档增量节奏、索引更新机制）** |
| **考察点** | "缓慢劣化 + 无变更 = 数据侧漂移"的直觉 + 数据闭环意识 |
| **好答案的形状** | 先问：文档库还在增量入库吗？入库质量有没有管控？→ 假设树：新入库文档解析质量差（扫描件/复杂排版）污染索引 / 切分参数与新文档类型不匹配 / 相似内容重复堆积挤占召回 / 无评测集所以劣化无告警；关键加分项：**提出先建固定评测集把"缓慢劣化"变成可量化曲线**——治本是把评测做成持续监控而不是一次性验收 |
| **危险信号** | 只想到"换 embedding 模型"；不问数据侧；无评测闭环意识（劣化半年才发现本身就是问题） |

#### T3 agent 长任务跑偏成环

| 栏目 | 内容 |
|------|------|
| **题面（口述）** | "一个多步骤 agent 任务，前几轮正常，越往后越跑偏，最后陷入重复动作。你怎么设计让它既不跑偏也不成环？" **（故意不说：任务时长、上下文窗口）** |
| **考察点** | 上下文管理 + 目标保持设计——长任务是 agent 最容易翻车的场景 |
| **好答案的形状** | 机理层：任务目标被中间结果稀释 → 跑偏；同类信息重复占据上下文 → 成环。设计层：每轮携带任务摘要与目标重注入 / 分段摘要压缩而非硬裁剪 / 调用签名去重 + 轮次预算 / 偏离检测（对任务目标打分，低于阈值回拉或转人工）。能区分"检测"与"止住"两层 = 真做过 |
| **危险信号** | 只答"用更强的模型"或"写好 prompt"；说不出目标稀释机理；不给兜底（转人工/熔断） |

## 第三部分：面试执行策略

### 3.1 面试节奏设计

以 `../SKILL.md` §分层标尺（SoT）及 Step 5“题型配比”的分层分钟预算为唯一来源，生成实际议程并核对各段之和等于总时长。开场触发关键核验项，项目/B 环节覆盖已确认适用的 N1-N5，C/D 保留岗位相关工程探查，E 按 SoT 预留一题手写、自测与边界解释；不另加笔试轮。缩短面试时减少重复原理问答与第二项目，不静默删除手写或已确认的成长证据；提前结束的缺口留待补验。

### 3.2 追问方法论

核心原则：**从具体到抽象，从做了什么到为什么这么做**

```
第一层：你做了什么？
  ↓
第二层：怎么做的？（技术选型、架构设计、数据流）
  ↓
第三层：为什么这么做？（为什么不用方案B？）
  ↓
第四层：怎么评估的？（baseline是什么？指标怎么定的？）
  ↓
第五层：有什么不足？如果重来会怎么改？
```

**从候选人B面试中提炼的有效追问模式**：

1. **链式追问**（从一个点深入到原理层）：
   - "你做了RAG？"→"向量模型用的什么？"→"为什么选这个？"→"cosine和点乘的区别？"→"应用上有什么区别？"
   
2. **闭环追问**（要求完整数据流）：
   - "能完整的讲一下数据流吗？从用户提问到最后的闭环"
   
3. **反例追问**（挑战方案合理性）：
   - "7B模型做不了意图识别吗？不调的话做不了吗？"
   - "退出就不做了吗？这个事谁来处理？"
   
4. **量化追问**（要求可衡量）：
   - "有没有量化指标？"
   - "微调前有没有baseline？"
   - "怎么衡量你的工作价值？"
   
5. **提示性追问**（给方向但不给答案）：
   - "给你个提醒，你可以看看智能体的一些构建策略"
   - 在候选人卡住时给方向，看他的学习能力和思维弹性

### 3.3 评分维度

每个候选人按以下维度打分（1-5分）：

| 维度 | 权重 | 1分 | 3分 | 5分 |
|------|------|-----|-----|-----|
| **AI工程化深度** | 30% | 会用框架但不懂原理 | 能独立设计RAG/Agent方案 | 能解决幻觉/评估等深层问题 |
| **架构设计能力** | 25% | 只做过单模块 | 能设计完整系统架构 | 能处理高并发/分布式等复杂场景 |
| **模型理解** | 15% | 只调API | 会微调/蒸馏 | 理解训练原理，能优化模型效果 |
| **量化评估意识** | 15% | 无量化意识 | 有数字但无baseline | 有完整的baseline→改进→评估闭环 |
| **独立负责能力** | 10% | 需要全程指导 | 能在指导下完成 | 能独立从0到1闭环 |
| **学习能力** | 5% | 只用熟悉的技术 | 能快速学新技术 | 能将新技术与业务结合 |

> **软性素质（按 JD 清单，AC-8 分层服从）**：上表是本岗位（专家岗）的**知识层**评分维度。**软性素质**不在此表另起分数，而是按 Step 2 产出的「JD 软性素质要求清单」逐项做「要求 × 表现」对比（见 `软性素质要求×表现对比-示例.md`），映射到现有元能力五项（自知力 / 态度-可管理性 / 可引导性 / 沟通 / 诚实度）。其权重与红线随层级变化，**取值派生自 SKILL.md §分层标尺（SoT）**：
> - **专家岗**：软性素质权重低（看深度）；中权重软性素质缺失 = 提示培养 / 搭配，非一票否决。
> - **外包 / 初级岗**：元能力**总权重**为 40-50%；可管理性、可引导性、沟通、自知力、诚实度及已确认的 N1-N5 映射项在此预算内分配、合并去重，不把总权重给某单项。真实缺口按已确认岗位权重处理。
> - **实习生岗**：「诚实度」一票否决。
>
> 判定三态：✅有证据支撑 / ❌缺失（有可引用的反向行为证据，进风险点）/ ❓未覆盖或存疑（中性，不扣分）。每条判定引用原文，无原文不下结论；问过但未能举例不等于缺失。

## 第五部分：常见候选人类型识别

### 5.1 "广度型"（候选人B类型）

**特征**：
- 简历项目多、技术栈广、有内容输出（书/博客/演讲）
- 什么都用过、什么都知道一些
- 往深了一问就卡住

**面试策略**：
- 选取1-2个核心项目，L3追问到底
- 重点考察：有没有一个方向是真正深入的
- 警惕：简历丰富 ≠ 技术深厚

### 5.2 "大厂螺丝钉型"

**特征**：
- 大厂背景，做过高并发/高可用系统
- 但只负责其中一个模块，缺乏全局视野
- 对"为什么这么做"答不上来

**面试策略**：
- 追问架构全貌，不只是他负责的模块
- 场景题考察系统设计能力
- 重点考察：能否从模块视角上升到系统视角

### 5.3 "学术转型型"

**特征**：
- 有论文、有算法基础
- 但工程落地经验少
- 写论文和做产品的思维模式不同

**面试策略**：
- 重点考察工程化能力：怎么部署、怎么监控、怎么处理线上问题
- 场景题考察产品思维
- 重点考察：能否把算法能力转化为业务价值

### 5.4 "包装过度型"

**特征**：
- 简历写得很漂亮，量化指标很多
- 但细节经不起追问
- 关键词堆砌

**面试策略**：
- 对每个量化指标追问baseline
- 要求完整数据流描述
- L3追问（为什么这么做）最能暴露

### 5.5 "全链路闭环型"

**特征**：
- 算法有顶会论文/专利背书，不是调参工，而是有原创性贡献
- 工程有生产级系统落地（高可用、高吞吐、完整的部署和监控体系）
- 管理有平台级架构视野（从数据基建→模型矩阵→智能体生态→业务效果量化）
- 量化意识贯穿始终：所有项目均有明确的 baseline→改进→结果 对比链
- 产学研一体：论文、专利、软著、业务落地形成闭环

**与其他类型的区分**：
- vs "广度型"：不只广，核心方向有论文级别的深度
- vs "大厂螺丝钉型"：是从0到1的负责人，有全局架构视野而非单一模块
- vs "学术转型型"：学术强但工程同样扎实，不存在"只会写论文不会落地"的问题
- vs "包装过度型"：量化指标有baseline对比，论文/专利可联网验证，经得起追问

**面试策略**：
- 重点不是验证真实性（经得起追问），而是评估**天花板在哪里**
- 考察维度应升级：从"能不能做"到"能不能带队做"
  - 技术选型的trade-off判断力（为什么不用方案C？）
  - 团队管理与跨部门协同能力（怎么协调多个团队？遇到阻力怎么解决？）
  - 技术路线规划能力（未来6-12个月的技术roadmap是什么？）
  - 对行业趋势的判断力（HR Tech/AI领域的下一步方向？）
- 场景题应给更高复杂度的设定（多系统协作、成本与效果平衡、技术债治理等）
- 关注短板：是否有明显的能力盲区（如后端架构偏某一语言栈、团队管理经验不足等）
- 这类候选人面试更像是**双向选择**，需要同时展示团队的技术实力和发展空间
